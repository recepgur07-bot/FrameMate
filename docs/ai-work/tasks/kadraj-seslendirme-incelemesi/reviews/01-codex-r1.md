## Kritik bulgular

- P1 — Every coach message sent through `SystemAccessibilityAnnouncer` uses `NSAccessibilityPriorityLevel.high` in `Sources/VideoRecorderApp/FrameCoach/SpeechCuePlayer.swift`. With `FrameCoachFeedbackFrequency.frequent` (zero minimum interval) and immediately accepted changed guidance, ordinary movement prompts can repeatedly interrupt VoiceOver navigation or another important announcement. Apple documents announcement priority as control over what may interrupt queued assistive speech; high priority should be reserved for genuinely urgent events. Use a queue/coalescing policy, a lower default priority for routine guidance, and explicit interruption rules. The plan currently asks about repetition but does not require this priority/queue audit. [Apple: AccessibilityNotification.Announcement](https://developer.apple.com/documentation/accessibility/accessibilitynotification/announcement)

- P1 — `lastAnnouncedSubjectCount` in `Sources/VideoRecorderApp/RecorderViewModel.swift` announces a count on the first single analysis with no temporal confirmation, while `FrameAnalysisService` accepts each Vision result, retains only the three largest faces, and synthesizes `confidence: 0.9`. A transient detection change such as one → two → one will produce count announcements and may combine them with different guidance; four or more faces are silently represented as `.three`. This does not meet the plan's intended examination of noisy person-count changes, priority, and multi-person edge cases. Add a stable-count state machine (N consistent analyses or time window), a graceful “three or more people” policy, reset behavior after sustained no-face state, and tests for flapping counts and 4+ detections.

- P2 — `SpatialCoachCuePlayer` is updated on every analyzed frame and has no independent debounce/hysteresis. `SpeechCuePlayer` rate-limits speech, but it does not rate-limit tones. Small detector jitter around `FrameCoachSpatialCueResolver` thresholds can continuously switch direction/severity; this is especially risky for users relying on sound rather than speech. The UI hint for `"Yön sesi"` says the sound arrives from the side where the face is, whereas the resolver emits the direction the user should move (for example, a left-of-center face produces `.right`). The plan should explicitly validate this user-facing semantic mismatch with blind users.

- P2 — `VisionFaceDetector` uses only `VNDetectFaceRectanglesRequest`, which returns face rectangles rather than stable identities, confidence values, body position, or occlusion state. The role labels `"soldaki kişi"`, `"ortadaki kişi"`, and `"sağdaki kişi"` are recomputed from horizontal sort order every frame, so they can swap when people cross or detection order changes. The source supports useful two- and three-person framing rules, but it does not establish who a person is across time. The review plan should require scenario testing for crossing people, partial faces, occlusion, and orientation/mirroring. Apple describes this request as face-rectangle detection and separately provides human-rectangle observations; neither API alone should be assumed to provide identity continuity. [Apple: VNDetectFaceRectanglesRequest](https://developer.apple.com/documentation/vision/vndetectfacerectanglesrequest?language=objc)

## Onaylanan kararlar

The wiring is coherent: `CameraOverlayRecorder` and the primary recorder deliver preview buffers; `RecorderViewModel.configureFrameCoachFeed()` sends them to `FrameAnalysisService`, `CaptureCoachingEngine`, `FrameCoachSpatialCueResolver`, `SpatialCoachCuePlayer`, and `SpeechCuePlayer`. `ContentView` exposes speech route, direction tones, centre confirmation, frequency, repeat interval, and on-screen text through bindings to `RecorderViewModel`, and `FrameCoachPreferences` carries the selected settings to the two players. The code has a clear rule priority in `FrameCoachingEngine` (clipping, overlap, scale, distance, spacing, individual vertical alignment, group alignment), gives group-oriented language for two and three people, suppresses a no-face message until three missing analyses, and locks a recently good frame for three seconds against non-hard guidance. Existing tests cover key single/two-person messages, low light, a brief face-loss case, route selection, repeated-text cooldown, and a generated stereo cue. `NSAccessibility.post(... .announcementRequested ...)` is an appropriate macOS mechanism for non-visual status changes and includes localized text and priority, as Apple requires. [Apple: NSAccessibilityAnnouncementRequestedNotification](https://developer.apple.com/documentation/appkit/nsaccessibilityannouncementrequestednotification)

## Riskli varsayımlar

The plan assumes that static code establishes whether phrases such as `"biraz sağa geç"`, `"kamerayı biraz yukarı al"`, and `"kadraj dengeli"` are understandable and actionable to blind users; that is doğrulanamadı without a VoiceOver user study or at least an observed VoiceOver session. It also assumes that stereo left/right is useful and correctly perceived with the intended outputs; speaker/mono routing, hearing asymmetry, and the mapping between camera preview orientation and the user's physical direction are doğrulanamadı. `SpeechCuePlayer` treats `NSWorkspace.shared.isVoiceOverEnabled` as the routing signal, but there is no inspected evidence that it observes a mid-session change or adapts an in-flight announcement. Apple’s SwiftUI accessibility guidance explicitly recommends exercising the app with VoiceOver and other assistive technologies, rather than relying only on inferred labels. [Apple: Accessibility fundamentals](https://developer.apple.com/documentation/swiftui/accessibility-fundamentals)

Personal Voice, Live Speech, Sound Recognition, and Point-and-Speak are not automatically applicable replacements for local visual framing guidance; no inspected product requirement supports collecting a voice model or interpreting surrounding text/sounds. Their absence is therefore not itself a defect. The better-supported opportunity is to use current accessibility announcement controls—priority and queueing—plus a user-selectable non-speech feedback path. Whether `AccessibilityNotification.Announcement` can replace the existing AppKit posting API on this app’s deployment target is doğrulanamadı from the inspected project configuration and must be availability-checked before it is proposed as an implementation requirement.
